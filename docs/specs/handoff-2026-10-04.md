## Part 1 — What shipped: ADR 0033, Home's component library (now CLOSED)

Full detail lives in `docs/specs/home-component-library/` (`00-overview.md` first, then the
per-component files) and `docs/decisions/README.md#0033`. Short version: Home's section
components (`src/slices/pages/ui/components/`) moved into `src/core/ui/` as reusable, pure
presentational primitives, split from their data-fetching composers (which stayed slice-owned).
**All 8 planned items, plus Footer added after the fact on request, are implemented and the user
visually verified them in a real browser (desktop + mobile)** — this spec set is done, no further
work expected on it.

`core/ui/` now exports (in addition to the original `cn`/`Container`/`Section`/`Eyebrow`/
`ButtonLink`): `Reveal`, `CountUp` (`motion/`), `Carousel`, `Hero`, `StatBand`,
`TwoColumnShowcase`, `PropertyCard`, `DualCtaPanels`, `NavBar`, `MobileDrawer`, `Footer`, plus the
dev-only `ScrollDebugProbe` + `debug-log.ts` helpers.

**Two real bugs were found and fixed by actually running the dev server** — neither showed up in
`typecheck`/`lint`, which is the main lesson to carry forward:
1. `Hero` importing `@core/media` (`MediaImage`) directly 500'd *every* page once `Hero` joined the
   `core/ui` barrel — any `"use client"` component anywhere that imports anything from `@core/ui`
   (e.g. `contact-dialog.tsx` importing `ButtonLink`) pulls the whole barrel's module graph into
   the browser bundle, including `@core/media`'s server-only `sharp`-based upload pipeline, which
   Turbopack can't chunk for the client. Fixed: `Hero` now takes a caller-built
   `background: ReactNode` prop instead, matching the pattern `TwoColumnShowcase`/`PropertyCard`/
   `DualCtaPanels` already used. **Any future `core/ui` component that needs an image must take
   `ReactNode`, never `@core/media` types directly** — this is now a hard rule, not just a style
   preference.
2. The `calc()` expressions passed to `Carousel`'s `basis` prop were missing the whitespace CSS
   requires around a binary `-` (`calc(100%-10px)` is invalid; `calc(100% - 10px)` is required).
   Routed through `Carousel`'s `var(--carousel-basis-*)` CSS-custom-property indirection, Safari
   resolved this into a runaway `flex-basis` — `document.documentElement.scrollHeight` ballooned
   past 25,000,000px while scrolling past the carousels, **only at desktop/tablet widths** (the
   broken `md`/`lg` values are never evaluated on mobile), which made the page feel like it could
   never reach its bottom. Fixed by adding the required spaces. Found via the debug logging in
   point 3 below, not by inspection — the symptom (scroll never finishing, sections below never
   revealing) did not look like a CSS typo from the outside.
3. **A new, reusable debugging tool exists now**: `Reveal` takes an optional `label` prop that
   console-logs (dev-only, no-op in production) when a section reveals and whether that was
   immediate (already in the initial viewport) or triggered by scroll; `ScrollDebugProbe` (mount
   once per page) logs viewport size on mount/resize and scroll position, and logs once when the
   page actually reaches its bottom. **Use these on every future page-redesign pass** instead of
   ad-hoc `console.log` — they're exactly what surfaced bug #2 above. Both are exported from
   `@core/ui`.

Verification method used throughout (no browser-automation tool was available this session, same
constraint as prior sessions): `pnpm typecheck && pnpm lint` after every change, `curl` against the
running dev server to check HTTP status + grep the rendered HTML for the right markup/data
attributes, then the user did the actual visual pass in Safari and pasted back console output when
something looked wrong (that's how both bugs above were actually caught and fixed).

**Process note for next time, if doing another fan-out-to-agents migration:** this session
launched several `Agent` calls with `isolation: "worktree"` in parallel to extract different
components at once. Worktrees can only `git merge --ff-only` onto **committed** history — they
cannot see uncommitted changes sitting in the primary checkout's working tree. The first attempt
left several components merged-but-uncommitted in the primary checkout between waves, which
blocked the next wave's agents (they correctly detected the mismatch and stopped rather than
guessing, per golden rule 6 — one even reconstructed the missing state by hand from the primary
checkout as a workaround, which worked but added risk and should be treated as a near-miss, not a
pattern to repeat). **Commit after every wave, before launching the next one**, if parallelizing
this way again.

## Part 2 — What's next: page-by-page `.mk` → `core/ui` migration, starting with Owners' hero

Agreed with the user (not written as a formal spec yet — do that first before touching code,
same process as Part 1): go through the remaining public pages **one at a time, together**,
replacing `.mk` HTML-string sections with the `core/ui` components from Part 1 where they match,
testing in the browser after each change. This is **not** the full `.mk`-vs-React paradigm
decision from `docs/specs/handoff-2026-10-03-b.md` Part 2 (that ADR-level question is still
separately open) — it's an incremental, section-by-section replacement using the
now-proven-in-browser component set, explicitly opted into by the user.

**First target, requested explicitly: the hero on `/[locale]/owners` (test URL used this session:
`http://localhost:3011/es/owners`).**

Already confirmed this session (`src/slices/pages/ui/owners-page.tsx`):
- Owners is a `.mk` page — its hero is a raw HTML string, not a React component:
  ```
  <section id="worth" class="hero compact owner-hero" style="padding:0">
    ${heroImgTag}
    <div class="wrap">
      <div class="hero-copy">
        <h1>${heroHeadline}</h1>
        <p>${esc(hero.copy)}</p>
        <div class="hero-cta" id="hero-contact-slot"></div>
      </div>
      <!-- earnings-estimate form card, second column -->
    </div>
  </section>
  ```
  with page-scoped CSS overrides (`.mk .owner-hero .wrap{grid-template-columns:1.1fr .9fr;...}`,
  `.mk .owner-hero h1{...}`, a `@media(max-width:980px)` stack-to-one-column rule) and a
  `HeroContactCta` client island slotted into `#hero-contact-slot` after the fact (About/Owners'
  `.mk` pages do this DOM-injection trick for interactive pieces inside HTML-string markup —
  understand it before touching this section, it's not a normal React child).
- The background image uses `mediaImgTag()` (ADR 0027's kernel `next/image`-backed HTML-string
  helper), **not** the React `MediaImage` component — different mechanism from Home's video hero
  entirely.
- **`core/ui/Hero` (from Part 1) already has an `aside` prop and a `compact` prop, both with doc
  comments that explicitly call out this exact Owners earnings-form use case** — they were carried
  over from the original `PageHero` component's doc comment (which already anticipated Owners
  using this layout) even though Owners was never actually wired up to it. **Check first whether
  extracting Owners' hero means generalizing/reusing the existing `Hero` with `aside={<earnings
  form>}` and `compact`, rather than building a second, separate hero component** — that's very
  likely the right move given the API was seemingly designed for exactly this, but confirm the
  visual result actually matches the current `.owner-hero` CSS (two-column `1.1fr .9fr` grid,
  `clamp(30px,4vw,50px)` headline, specific `hero-cta` margin) before assuming the existing
  component's generic layout is pixel-identical — it may need adjustment, which would itself need
  to not break Home's hero.
- `MediaImage` note: `heroImgTag` on this page could very likely be swapped for `core/ui/Hero`
  rendering a real `<MediaImage>` passed in via the new `background: ReactNode` prop (same pattern
  Home's video now uses) — but this is still-image, not video, so double-check `MediaImage`'s own
  props fit (it already supports stills, Home's prior non-Hero usages throughout the `.mk` pages
  all go through `mediaImgTag()` instead specifically because of ADR 0027 — read that ADR before
  assuming the switch is free; ADR 0027 explicitly rejected rewriting `.mk` pages into JSX for
  unrelated reasons, so moving *one section* of one `.mk` page into JSX, as agreed this session,
  is a narrower move than what that ADR was about, but still worth being deliberate about).
