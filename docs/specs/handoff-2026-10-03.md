### 2. Hero proportions unified across About, Real Estate, Buildings, Guests (`bd55956`, `eebcf60`)

Started from one complaint ("About's hero looks too tall vs. Real Estate's") and iterated to a
shared fix applied to all four `.hero.compact` sections in the app (Owners' hero is a separate,
already-tuned component and was not touched). Three findings worth knowing before touching any
hero again:

1. **The kernel's base hero is bottom-anchored with asymmetric padding**
   (`src/app/mock.css:62-70`: `align-items:flex-end`, `.wrap{padding-top:130px;
   padding-bottom:88px}`), which reads as "tall" — fixed per-page with
   `align-items:center` + `.wrap{padding-top:40px;padding-bottom:40px}`, scoped via each
   page's own `.mk[data-page="..."]` hook. (Real Estate already had this from a prior session;
   About/Buildings/Guests did not.)
2. **Widening `.wrap` does nothing by itself.** The actual line-wrap width is governed by the
   kernel's `.mk .hero h1{max-width:15ch}` / `.mk .hero p{max-width:46ch}` — both far narrower
   than `.wrap`'s own box. The first attempt (this session) widened `.wrap` to full-bleed
   (`max-width:none`) and saw **zero change** in the rendered text column width, because `h1`/
   `p` were still capping themselves independently. Fixed by overriding `h1{max-width:26ch}` /
   `p{max-width:60ch}` per page — this is what actually shortens the block (fewer, wider lines).
3. **Full-bleed broke both centering and legibility.** Setting `.wrap{margin:0}` (instead of
   `margin:0 auto`) pushed the text flush against the hero's left edge instead of keeping it a
   centred block — user caught this immediately ("antes estaban centrados"). Also, `align-items:
   center` moves the text into the vertical middle of the hero image, which is the **lightest**
   band of the kernel's default gradient (`rgba(...,.12)` at the 42% stop) — legibility dropped
   until the gradient was strengthened/evened out per page.

**Final pattern applied identically to all four pages** (`about-page.tsx`, `real-estate-page.tsx`,
`guest-page.tsx` — all `pages` slice — and `buildings-listing.tsx` — `buildings` slice), each as
a `.mk[data-page="<page>"]`-scoped block in that file's own `PAGE_STYLE`:

```css
.mk[data-page="X"] .hero{align-items:center}
.mk[data-page="X"] .hero .wrap{max-width:1600px;margin:0 auto;padding-top:40px;padding-bottom:40px;padding-left:40px;padding-right:40px}
.mk[data-page="X"] .hero h1{max-width:26ch}
.mk[data-page="X"] .hero p{max-width:60ch}
.mk[data-page="X"] .hero::after{background:linear-gradient(180deg,rgba(18,16,13,.46) 0%,rgba(18,16,13,.36) 45%,rgba(18,16,13,.8) 100%)}
```

Real Estate and Buildings already had their own `::after` overrides from a prior session (`.5/
.4/.82` and `.46/.34/.88` respectively) — Buildings' middle stop was nudged from `.34` to `.46`
to even it out for the same reason; Real Estate's was left as-is (already sufficiently uniform).

No kernel file (`src/app/mock.css`) was touched — every change is a page-scoped override inside
the owning slice, per Golden Rule 1/3.

### 3. About's "How We Started" section had a disconnected gap under the hero

`#story` (directly under the hero) inherited the kernel's generic `.mk section{padding:
var(--section-y) 0}` (`clamp(72px,10vw,150px)`, ~127px at the viewport checked). Right under
the hero's own bottom padding, that read as a large dead gap. Trimmed with
`.mk[data-page="about"] #story{padding-top:50px}` — `pages` slice only, this section only (not
a kernel change, doesn't affect `--section-y` anywhere else).

## Deferred / known gaps

- **Hero heights are now visually consistent but not pixel-identical** — `h1`/`p` max-widths
  are the same `26ch`/`60ch` across all four pages, but each page's copy is a different length,
  so line-wrap count (and therefore exact block height) can still differ by a line. Not fixed
  further this session; ask before chasing pixel parity — it'd mean either fixing a line-clamp/
  explicit height or editing copy length.
- **The "What We Stand For" duplicate label** in the About nav dropdown is intentional (mirrors
  the page's own duplicate eyebrow text) but is a slightly odd UX moment — two identical labels
  pointing at two different sections. Flagged to the user; they didn't ask for it to change.
- **Owners' hero was not touched** — it already has its own bespoke treatment (it doubles as
  that page's section sub-nav, pinned open on scroll — see `OWNERS_NAV_CSS` in
  `site-header.tsx`) and was out of scope for this round of hero unification.
- The `r2.dev` rate-limit issue from the previous session was re-checked once this session
  (single non-looping `curl` on two URLs) and was **still 404** — not retried further. See the
  previous handoff (`handoff-2026-10-02-d.md`) for the full writeup and the recommended fix
  (map a custom domain to the R2 bucket, set `R2_PUBLIC_BASE_URL`). Not addressed this session —
  still an open, real production risk.
