## Bug fixed this session (read before re-running the seed)

`writeGuidePage()` deletes and reinserts every `guide_section` row on every run (sections have
no public identity to diff against), but the original version of this logic (written earlier
this session, before being caught) **never deleted the old section's `header_media_id`
asset** — only `resolveImage()`'s hero-level cleanup existed. Every re-run was silently
leaking an R2 object + `media_asset` row per section with an image. Fixed by adding the same
`isSeedOwnedCredit`-gated cleanup for section headers before the delete+reinsert. **62
orphaned assets from earlier runs this session were found and deleted** (R2 objects + DB rows
+ `alt` translations) as part of landing this fix — none were staff-uploaded (all matched the
`Pexels ·`/`Unsplash ·`/`Wikimedia Commons` credit prefixes this script owns). Re-ran the seed
afterward and confirmed 0 orphans, all 67 seed-owned assets referenced.

If you edit `scripts/seed-guides.ts` again: the cleanup only ever deletes assets whose
`media_asset.credit` matches `SEED_CREDIT_PREFIXES` — never touches anything a staff member
uploaded through the (future) admin media picker.

## ⚠️ R2 public dev domain (`r2.dev`) rate limit — real finding, not local-only

Mid-session, all 67 guide images (and even an unrelated pre-existing asset,
`blog/lisbon-cover.jpg`) started returning 404 via
`https://pub-9abd9259e8d44b439c0d61c790223db5.r2.dev/...`. Spent real time chasing this as a
possible data-loss bug (checked a concurrent peer session, checked for R2 lifecycle rules,
checked bucket identity) before confirming the actual cause: **the public `r2.dev` dev
subdomain rate-limits/deprioritizes under sustained request volume**, and this session's own
verification tooling (dozens of rapid `curl` checks across all 67 images, repeatedly, plus
several dev-server restarts each re-fetching images) triggered it. Confirmed via our own S3
credentials (`HeadObjectCommand`) that **every object was always intact** in the bucket the
whole time — this was purely a public-access-layer symptom, not data loss. Still 404 as of
session end (checked once, non-looping, ~90s after first noticing it — did not wait longer).

**Recommended fix, not done this session**: map a custom domain to the R2 bucket in the
Cloudflare dashboard and set `R2_PUBLIC_BASE_URL` to it (the code already reads this env var —
`src/core/media/server/r2.ts` already prefers it over the generic host). This isn't just a
dev-environment annoyance: if Next's image optimizer or real guest traffic hit `r2.dev` at
production volume, the same rate limit would degrade the live site. Worth doing before launch
regardless of this session's incident.
