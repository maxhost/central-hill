## ⚠️ One thing to know before touching the database again

This session had live read/write access to the user's real Neon `DATABASE_URL` (given to set
up local dev) and used it twice, outside the app's own publish/revalidate path:

1. Read `page_content` (`home` row) directly via `psql`-equivalent scripts (`@neondatabase/serverless`
   + a throwaway `.mjs` file, deleted after each use) to diagnose the stale-URL bug above.
2. **Wrote** to it once: backfilled `data.dual_cta` on the `home` row (English copy, matching
   `scripts/seed-demo.ts`'s historical defaults) because the schema now requires that field and
   the row predates it — without this, the section would only ever show the i18n fallback text.

**It was never confirmed whether this Neon instance is production or a dev/staging database.**
Treat it as production until told otherwise. The write above was additive (added a missing
key, touched nothing else) and mirrors exactly what `scripts/seed-demo.ts` would produce, but
it bypassed `unstable_cache`'s tag-based revalidation (`page:home`) — harmless in `next dev`
(no persistent cache), but **if this ever runs against a deployed/ISR build, that row's cache
needs an explicit revalidate** (or just re-save it from the backoffice once D-something ships
a Home editor screen for `dual_cta`).
