## Part 1 — What changed this session (animation pass)

Client feedback: the About page (specifically "How We Started" → "Our Structure") read too static;
wanted subtle animation/motion/icons/transitions without leaving the locked Warm Editorial visual
system. This grew, page by page, into the same treatment applied to every public page.

### The pattern established

Two different mechanisms, because the codebase has two different page-building paradigms (see
Part 2):

1. **`.mk` HTML-string pages** (About/Guests/Owners/Real Estate, `pages` slice; Buildings listing,
   `buildings` slice) — each page's own `PAGE_STYLE` gets:
   ```css
   .mk[data-page="X"] .reveal-io{transition:opacity .7s var(--ease),transform .7s var(--ease)}
   .mk[data-page="X"] .reveal-io.pre-reveal{opacity:0;transform:translateY(18px)}
   ```
   Elements that should animate carry `reveal-io pre-reveal` (and `reveal-stagger` if they're a
   grid of siblings that should stagger in). The hidden state (`.pre-reveal`) is baked straight into
   the **server-rendered** markup — not toggled on by JS after the fact — so there is no flash of
   visible-then-hidden, and a `<noscript>` rule (`[data-page="X"] .pre-reveal{opacity:1!important;
   transform:none!important}`) keeps content visible with JS off. A client island,
   `<ScrollReveal page="X">` (`src/slices/pages/ui/components/scroll-reveal.tsx`), removes
   `.pre-reveal` immediately on mount for anything already in the initial viewport (one clean
   fade-in, no scroll needed) and via `IntersectionObserver` for anything below the fold. It
   honours `prefers-reduced-motion`.

   **`ScrollReveal` is duplicated**, not imported, into `src/slices/buildings/ui/components/
   scroll-reveal.tsx` — Buildings is a different slice from `pages`, and slices only talk through
   `contract.ts` (golden rule 2), so the component was copied rather than cross-slice-imported.
   This is itself a small, fresh instance of the exact duplication problem Part 2 is about — flagged
   there as a known example, not re-litigated here.

2. **Home** (`src/slices/pages/ui/home-page.tsx`) has **no** `.mk` wrapper at all — it's composed of
   real React/Tailwind components (see Part 2). The `.mk` mechanism doesn't apply, so a parallel
   React wrapper was built instead: `<Reveal>` (`src/slices/pages/ui/components/reveal.tsx`), a
   `"use client"` component using the same timing (0.7s, 18px, Tailwind's `ease-in-out` — which *is*
   `cubic-bezier(.4,0,.2,1)`, the same curve `var(--ease)` uses elsewhere) via Tailwind utility
   classes and one `IntersectionObserver`. `prefers-reduced-motion` is handled via CSS
   `motion-reduce:` variants, not a JS check (avoids a React `set-state-in-effect` lint violation
   and is more correct anyway). Each Home section is wrapped **at the `home-page.tsx` call site**
   (`<Reveal><StatsBand .../></Reveal>`, etc.), not edited internally — `FeaturedPortfolio` is also
   rendered by the Guest page, so animating it had to happen at Home's call site to avoid changing
   Guest's rendering.

**Consistent rules applied everywhere**, worth knowing before touching this again:
- **Hero is never animated**, on any page — it's the LCP element and every other page already
  treats it this way.
- **Card grids** (3+ visually-identical siblings) get `reveal-stagger` + hover (lift + shadow,
  icon lift/scale) if they don't already have hover from a prior session.
- **Single or paired blocks** (image+text, two CTA panels, intro+form) get reveal only, no hover,
  no stagger — this split was applied consistently across every page once established on About.
- Shared cross-page islands (`FaqSection`, `TestimonialsRow`, `FeaturedPortfolio`) were **never**
  edited internally — always left alone or wrapped from the specific page's call site — because
  touching them changes every page that renders them.

**Gate:** `pnpm typecheck` clean and `pnpm lint` 0 errors (same 5 pre-existing warnings as every

in a real browser** — no browser automation tool was available this session, same caveat as the

## Part 2 — The architecture question (read before drafting anything)

### What the user asked for

Mid-session, the user flagged — correctly — that the codebase has **two different page-building
systems**:

1. **`.mk` pages** (About, Guests, Owners, Real Estate, Buildings, Services, and presumably
   Blog/Guides — **not all independently confirmed this session, verify**): large HTML-string
   template literals injected via `dangerouslySetInnerHTML`, styled by `src/app/mock.css` (shared)
   plus a per-page `PAGE_STYLE` constant, scoped via `.mk[data-page="X"]`. Content that's
   DB-driven gets interpolated with manual `esc()`/`escAttr()` escaping. Each page's own doc
   comment says it's "the approved `mock/X.html` embedded 1:1" — these were built to port
   client-approved static mockups quickly, not as the intended long-term architecture.
2. **Home** (and only Home, confirmed this session): real React components composed in
   `home-page.tsx`, built on `@core/ui` (`Container`, `Section`, `ButtonLink`, `Eyebrow`) + Tailwind
   utility classes directly in JSX. No `.mk`, no raw HTML strings, no manual escaping (JSX
   auto-escapes).

The user wants: **one ADR + a page-by-page migration plan** to unify onto a single system,
prioritizing **SEO/GEO, hyper-fast loading, and backoffice-form-driven content editing** — and
explicitly wants a **cross-page inventory of duplicate/near-duplicate components first**, so the
plan builds each shared piece once rather than reimplementing it per page. Direct quote (translated):
*"we need to identify which components are identical across pages so we build them once and reuse
them in the plan — there are more than it seems."* The actual migration would happen later,
page-by-page, across many future sessions — **this next session's job is survey + ADR + plan only,
not implementation.**

### ⚠️ Critical prior art — found this session, changes the shape of the decision

Before writing anything, **read `docs/decisions/README.md` in full** (1108 lines — long, but every
ADR there is short and this is explicitly what golden rule 6 says to consult before a cross-cutting
call). Two entries are directly on point and were **not known to me when I gave the user my
first-pass recommendation mid-session** (I'd recommended migrating everything to React/Tailwind,
reasoning from icon-loading cost, CSS duplication, and escaping-risk alone — before I'd read these):

- **ADR 0027** faced almost exactly this question already, narrowly: nine `.mk` pages' images were
  bypassing the optimizer (`mediaImgTag`/blurhash never wired into the HTML-string builders). The
  ADR explicitly considered rewriting those pages into JSX and **rejected it**: *"Rewriting nine
  pages back into JSX is large, risky, touches several slices and buys the user nothing."* It chose
  a kernel-level fix instead (`mediaImgTag()`, built on `next/image`'s `getImageProps()`, emitting
  an optimized `<img>` as a string) that fixed the actual defect without touching the page paradigm.
- **ADR 0023 ("Update 2" and "Update 4")** found, while restyling Owners' `why`/`services`/
  `dashboard` sections to match layouts that already existed as Tailwind components on Home
  (`OwnersSection`-equivalent / `GuestsSection`'s "Image Showcase"), that **dropping a Tailwind
  component inside an `.mk` page leaks styles** — `mock.css` styles bare elements (`.mk h2, h3, a,
  section`), so a Tailwind component rendered inside that wrapper inherits those rules
  unpredictably. Both times, the resolution was to **reproduce the Tailwind layout as new, scoped
  `.mk` CSS** rather than import the component. This is a real, demonstrated technical obstacle to
  incremental mixing, not a hypothetical one — any migration plan has to either solve this
  (e.g., render the new component *outside* the `.mk` wrapper, the way `FaqSection`/
  `TestimonialsRow`/`FeaturedPortfolio` already do today) or account for it directly.
- **ADR 0022**, for contrast, is a precedent that migration *into* the component system has worked
  before — Home itself was re-skinned from a mock-derived page into `@core/ui`/Tailwind components
  under that ADR. Worth reading as a feasibility template, not just as history.

**Re-examine, don't rubber-stamp, my earlier recommendation.** Before finding the above, I told the
user I'd recommend unifying onto React/Tailwind. Holding that against what the user actually
prioritized (SEO/GEO, speed, backoffice-editable content), it's worth being honest that **none of
those three are obviously blocked by staying in the `.mk` paradigm today**:
- SEO/GEO structured data (`src/core/seo/json-ld.tsx`) is already centralized kernel infrastructure,
  usable identically from either paradigm — confirmed this session, not a differentiator.
- Both paradigms already render through Next ISR, DB-free at request time (ADR 0002) — no speed
  difference there. `mediaImgTag()` (ADR 0027) already gives `.mk` pages the same `next/image`
  optimizer pipeline Home's components use directly — also not a differentiator anymore (it was
  before ADR 0027 shipped).
- Most `.mk` pages already pull content from `page_content` DB rows through Zod-validated schemas
  (ADR 0012) — Guests/Owners/Real Estate/Buildings are already backoffice-editable today; **About
  is the one exception, still 100% hardcoded** (its own file comment says so explicitly) — that's
  arguably a bigger, narrower gap than "wrong rendering paradigm."

The **real, demonstrated** pain — confirmed firsthand this session, not theoretical — is **component
and CSS duplication**: I personally had to copy-paste CSS and even duplicate a whole JS component
(`scroll-reveal.tsx`) across slices this session because there's no shared place for it to live. The
inventory below is further, stronger evidence of the same thing, pre-existing before this session.
**That problem is real and worth solving. It does not, on its own, prove a full rewrite is the only
or best fix** — ADR 0027 solved a similarly-shaped problem without one.

**Give the next session room to reach its own conclusion, with at least three options genuinely
weighed, not just "how do we rewrite everything":**
1. **Full migration** — every `.mk` page becomes React/Tailwind/`@core/ui` components, matching
   Home. Strongest for type safety, DX, and stopping the drift for good. Carries the real risks
   ADR 0027 named: large, multi-slice, pixel-fidelity risk against approved mockups, many weeks of
   work before any user-visible benefit lands.
2. **Extract shared patterns within the `.mk` paradigm** — promote the repeated CSS blocks (see
   inventory below) into `mock.css` once, and build shared, parameterized **HTML-string-generator
   functions** (mirrors what ADR 0027 did for `mediaImgTag()` — a kernel-level, additive fix, not a
   page rewrite) for the patterns that repeat across pages. Solves the duplication pain directly,
   much lower risk, doesn't achieve "one system" or type safety.
3. **Hybrid/incremental** — new pages and any page already getting heavy edits migrate to React/
   Tailwind going forward (stops the drift from growing); stable, rarely-touched `.mk` pages stay as
   they are; shared *patterns* get extracted regardless of which paradigm ends up consuming them
   (a pattern extracted per option 2 is reusable from a future React component too, if its data
   shape is kept clean). Lowest risk, slowest convergence, matches how Home itself seems to have
   been treated as the "pilot" that already proved the target system works.

Whatever the next session recommends, it should state the reasoning against the user's three
stated priorities explicitly, the way the ADRs in this repo already do, and should **get the
user's explicit sign-off on the ADR's Decision before any migration implementation starts** — same
as every existing ADR's "Status: Accepted" implies, and same as this user has required explicit
go-ahead at every step this session.
